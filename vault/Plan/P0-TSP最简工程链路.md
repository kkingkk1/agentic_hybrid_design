# P0-TSP最简工程链路

所属[主计划](多智能体协作的通用混合算法自动设计.md)维护阶段状态；本文件维护P0任务和验收。

## 目标与进入条件

以小预算走通“问题合同 → 完整程序生成 → 独立评价 → 冻结后运行”，并保存原始记录。本机资源和访问边界遵循主计划第2.3节。

P0只验证工程链路，可以使用单一机制，不要求填满种群或完成五角色比较。工程通过不代表混合设计能力或性能目标已得到验证。

本阶段参考[启发式设计项目的P0工程验收](../../../agentic_heuristic_design/vault/Plan/mechanisms/P0-单任务一代接入与验收.md)。该项目设计ACO框架中的启发式函数，本项目生成完整求解程序，不依赖另一项目的可变运行文件。

## 任务与验收

### ☑ 任务1：确定问题与运行合同

**动作：** 确定TSP实例、求解接口、实现环境、模型调用方式及本批预算。

**交付物：** 本节合同、[实例清单](../../data/p0_tsp/manifest.json)、实例快照与[生成器](../../scripts/generate_p0_tsp.py)。

**验收：** 已确定首批合同和隔离设计；评价器、隔离、模型可用性及预算执行方式仍须在真实生成前通过检查。

#### 实例与接口

- 首批采用[RoCo预印本v2表7](https://arxiv.org/html/2512.03762v2)的两组TSP训练规格：5个50节点和10个200节点实例，仅用于P0工程检查。坐标在单位正方形均匀采样，使用未取整的欧氏距离；规格来源不要求采用ACO或GLS。
- [50节点](../../data/p0_tsp/train50.json)和[200节点](../../data/p0_tsp/train200.json)快照取自参考数据，并按ReEvo生成规则逐项核验。来源、版本、种子、校验值和实例ID见清单；尚不能认定与RoCo作者实际实验文件相同。可在项目根目录运行 `python -B scripts/generate_p0_tsp.py --verify` 核验快照。
- 数据文件是“实例、城市、二维坐标”的三维JSON数组；实例ID由 `tsp50-` 或 `tsp200-` 加从0开始的三位索引构成。候选从标准输入接收一个UTF-8 JSON对象：`coordinates` 为有限数值组成的二维点数组，`seed` 为非负整数，`time_limit_ms` 为正整数。时限从进程启动起计算，包含读取和初始化。
- 标准输出只允许一个UTF-8 JSON对象，必含城市编号数组 `tour`，可附有限数值 `objective`；调试信息写入标准错误。路径须恰好包含每个城市一次，编号为0至城市数减1的整数，不接受布尔值或重复终点。目标为最小化闭合回路的未取整欧氏距离之和，由独立评价器计算，不采信声明目标值；非零退出码、非法数值或不符合格式均判失败。

#### 环境与模型

- 候选使用CPython 3.13.12标准库，单文件 `solver.py`，求解入口为 `python -I -B solver.py`。构建阶段在独立隔离环境中只做语法编译检查，不执行候选代码；实际使用已核验的解释器路径。
- 使用本机Codex CLI 0.163.0与已有订阅模型 `gpt-5.6-luna`，通过 `codex exec --json --ephemeral --output-schema` 调用，不自动切换账号或付费API。[响应格式](../../cfg/p0_model_response.schema.json)只允许 `thought` 和 `code` 两个字符串字段，分别提供简要算法思路和完整源码；宿主另检查二者非空。
- 关闭 `shell_tool`、无限重连及客户端请求和流重试。`unified_exec` 请求关闭后仍显示开启，不能假定关闭：模型进程须直接运行于限制活动进程数为1且不允许breakaway的Windows作业对象中。基础探针已阻止普通子进程，但尚未证明实际 `codex exec` 或既有外部服务受限；真实生成前须核验模型执行边界、登录、额度、模型和接口。出现非预期工具事件或无法核实的重试时停止。

#### 本批预算与停止规则

以下是运行上限或停止阈值，不是已发生的消耗。真实生成须先通过任务2、3。

- 最多3次CLI调用尝试，包含初始生成、修复和基础设施重试，最多形成3个程序版本。累计已报告输入、输出达到150,000 token即停止；缓存输入与推理输出已计入总量时不重复计算。单次调用可能超过该阈值；失败调用的用量或内部重试次数无法核实则记为未知并停止。
- 每个版本在15个实例上各运行一次，求解种子均为0；冻结后重跑同一批。失败版本可提前停止，但不算通过全批评价。单实例从进程启动至完整输出的墙钟上限为15秒；单次构建或语法检查上限为30秒。
- 从首次真实生成到冻结运行完成，墙钟上限60分钟，包含资源等待；构建、求解和独立评价累计CPU上限1,200核秒。任务2、3的事前检查和探针消耗另记，并计入P0总实耗。
- 每个求解作业的标准输出上限16 KiB、标准错误上限64 KiB；单次模型响应上限1 MiB。超时、超限、解析或构建失败和非法解均记为失败并计入消耗；达到上限或无法可靠计数时停止。
- 核分配遵循主计划第2.3节及[核映射检查](../../scripts/p0_cpu_topology.py)：15个实例使用前15个槽位，剩余槽位不用于重复运行。调度前在自身上下文重验拓扑、实例清单与可用掩码；变化时停止。映射不保证操作系统层面的独占。

### ☑ 任务2：接入实例解析与独立评价

**动作：** 按任务1的接口接入实例解析、完整路径校验和独立目标计算。

**交付物：** [实例解析与评价入口](../../scripts/p0_tsp_evaluator.py)、[检查测试](../../tests/test_p0_tsp_evaluator.py)和[验收记录](../../outputs/p0_task2_validation_20261105_final.log)。验收记录保存在本机，不纳入Git。

**验收：** 小实例结果与手算或独立枚举一致；能识别漏访、重复、非法节点与非法数值，并对伪造目标声明使用重算值。只接受时限内收到的完整合法解；构建与独立验解另行计时。检查失败先修正并重验。

入口的 `input` 子命令构造求解输入，`evaluate` 子命令从标准输入读取求解输出。实际退出码和耗时须由可信宿主提供；进程监督、计时和隔离仍由任务3、4实现。运行 `python -B scripts/p0_tsp_evaluator.py evaluate --help` 查看参数。

### ☐ 任务3：核验隔离与资源限制

**动作：** 实现选定的构建、求解隔离和监督方式，用无害探针检查网络、数据和资源边界。

**交付物：** 探针源码、输入、预期与实际结果，以及失败和重验记录。

**验收：** 构建与运行环境的网络和数据隔离，以及求解作业的进程、线程、内存、时限和16槽位绑定通过检查。使用模拟敏感文件，记录越界被阻止或作业被终止；探针只证明已检查的边界。失败先修复并重验，通过前不构建或执行生成代码。

- 每个构建或求解作业使用不同身份的[AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)，不授予网络能力，只开放自身代码、必要Python运行文件及输入输出通道；构建与运行分开隔离。执行前明确配置、可访问路径及创建和清理方式；涉及用户环境变更时按项目授权规则处理。
- 求解进程恢复执行前加入[Windows作业对象](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)，限制单进程、物理核映射、512 MiB内存和超时，禁止breakaway。探针检查退出状态、实际绑定、16个槽位，以及内存提交量和工作集的限制与记录方式。
- 单线程通过独立ETW会话按PID过滤线程创建事件。恢复执行前登记PID、主线程ID并启用过滤，只接收已登记作业的事件；按事件负载识别进程和线程，不能把事件头PID直接视为目标线程所属进程。发现额外线程时终止仍在运行的作业并判失败；作业已结束也不接受结果。事件处理完成且确认无丢失后才能接受结果。
- 分别测试普通线程和隐藏调试事件线程；检查PID过滤、事件丢失、结果接收顺序及会话创建和清理。每个PID过滤器最多8个进程，16并行须使用足够的独立会话；不得连接、停止或修改现有 `NT Kernel Logger`。无法安全启用、过滤或证实监测完整性时停止并回到任务1重新选型，不启动真实生成。[本机选型记录](../../outputs/p0_task1_diagnostics_20261105.md)不代替正式探针；该记录保存在本机且不纳入Git。

### ☐ 任务4：真实生成、构建与评价

**动作：** 任务2、3及模型运行前检查通过后，生成完整TSP求解程序，构建并独立评价。

**交付物：** 原始请求与响应、版本化源码、构建和运行记录、独立评价及实耗。

**验收：** 至少一条真实生成、构建和评价链路完成，程序在本批实例上提交合法完整解，目标由独立程序重算。出现错误时记录原因；预算内可修复解析、构建、接口或执行错误，但不根据解质量反馈演化算法方案。

每个版本分别保存和评价，不覆盖旧版或沿用其他版本的分数。逐版本关联请求、响应、CLI原始事件、源码、标准输出、标准错误、退出状态、评价和资源消耗；分别记录调用次数、版本数和通过评价的版本数。模型调用不执行生成的求解程序。

### ☐ 任务5：冻结程序并验证独立运行

**动作：** 冻结通过工程评价的源码、依赖、运行配置和构建产物，保存文件摘要并关联评价记录，在无模型服务访问的环境中重跑本批实例。

**交付物：** 冻结程序及运行配置、独立运行记录和评价结果。

**验收：** 冻结程序无需模型服务即可按合同运行，全部实例通过独立验解和目标重算。失败时记录原因，修复后重新评价和冻结，不将失败记录当作通过。

## 完成条件与停止处理

评价器和隔离探针通过检查，至少一条真实生成、评价和冻结运行链路通过，且错误与资源限制可检查、记录可追溯，P0才算完成。原始请求响应、代码、输出、评价、实耗和探针记录保存至[outputs/](../../outputs/)，不以摘要代替原始记录。

预算耗尽、必要条件未确定或检查未通过时停止相应操作并报告原因；P1进入条件由主计划决定。
