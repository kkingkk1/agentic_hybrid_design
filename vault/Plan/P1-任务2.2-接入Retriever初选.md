## 设计原理

Retriever 在初始化时为混合方案设计准备参考材料。问题分析给出检索目标。算法候选提供可复用方法和组件的线索，案例候选提供组件衔接、数据传递和适用范围的线索。

任务 2.2 让模型根据目标问题的约束、表示和设计需求，在两个库的全量目录中判断相关性。每次初选请求都提供同一快照的完整候选目录，类别只作判断参考。模型给出选择和理由，程序核对格式、ID 范围、分组及唯一性，并将结果绑定到本轮快照。

任务 2.3 沿用该快照，按选中或补读的 ID 加载完整说明、代码和来源，再提供给 Retriever。初选让模型比较全量候选，全文请求只覆盖需要深入核验的材料。初选理由提供相关性判断，适用性和引用在全文阶段依据实收材料核验。

## 输入与输出

### 入口输入

- **问题分析** 包含问题结构、原目标与约束、设计需求。受控验收和真实试跑可直接传入样例，正式问题分析者在任务 2.4 接入。
- **快照与接口** 调用方持有本轮固定的 `RetrievalSnapshot`，通过其 `record` 回调收集读取事件，并提供模型调用和请求响应记录接口。模型调用接收完整请求并返回原始响应文本。

### 模型请求

请求包含初选指令和以下三组数据。

- `problem_analysis` 提供目标问题与选择依据。下方 CVRP 样例用于受控验收和真实试跑，原问题约束来自[主计划](多智能体协作的通用混合算法自动设计.md)。
- `algorithms` 来自 `catalog()` 的完整算法组。正式首版每项包含 `algorithm_id`、`category` 和 `summary`。摘要提供功能、适用问题与必要边界。
- `cases` 来自 `catalog()` 的完整案例组。正式首版每项包含 `case_id`、`category` 和完整 `description`。描述提供组合机制与组件衔接线索。

CVRP 样例的 `problem_analysis` 如下。实际请求另附上述两组完整候选。

```json
{
  "problem": "CVRP",
  "problem_structure": "将客户分配到多条车辆路线，并确定各路线的访问顺序。",
  "objective": "最小化按未取整欧氏距离计算的总路线距离。",
  "constraints": ["单仓库", "同质车辆容量", "每位客户服务一次，需求不拆分", "使用车辆数可变"],
  "design_needs": ["考察将客户排列解码为容量可行路线的方法", "查找解码与局部改进相衔接的案例"]
}
```

### 模型响应

要求模型返回一个 JSON 对象，只含 `algorithms` 与 `cases` 两个数组。每项只含精确的字符串 `id` 和去除首尾空白后仍非空的字符串 `reason`。理由根据目录说明候选和设计需求的关系，将候选信息中无法判断的适用条件标为待核实。每组均可为空。

```json
{
  "algorithms": [
    {"id": "ALG-001", "reason": "Split 可为客户排列到路线的解码提供参考，容量罚项如何衔接本项目的可行性要求待核实。"}
  ],
  "cases": [
    {"id": "CASE-001", "reason": "展示交叉、Split 解码和局部搜索之间的衔接。"}
  ]
}
```

### 程序交接输出

整批校验通过后交接以下字段。

- `selection` 保存整批校验通过的分组 ID 和理由。
- `selected_ids` 先列算法 ID，再列案例 ID，保留组内顺序。上例得到 `["ALG-001", "CASE-001"]`。
- `snapshot_id` 和 `manifest_sha256` 来自本次 `catalog()` 的成功读取事件。调用方保留同一个快照实例，供任务 2.3 使用 `selected_ids` 加载材料。

两组都为空时，照常交接上述字段，`selected_ids` 为 `[]`，记录「本轮未选中材料」。任务 2.3 跳过初选材料加载并记录缺口。能确定补读条目且满足本轮快照、预算与停止条件时可补读，其余情况按任务 2.3 的规则结束检索并报告缺口。

## 实施步骤

拟新增 `scripts/p1_retriever.py` 和 `tests/test_p1_retriever.py`。

1. 用本轮快照调用 `catalog()`，以本次调用的成功事件确定目录版本。无法核验快照或关联成功事件时，记录原因并停止本次调用。
2. 用初选指令、问题分析和两组完整候选组装请求，核对两组候选与目录逐项一致后，记录实际交给模型调用接口的完整请求。候选缺失、截断或与目录不符时停止本次调用并记录原因。
3. 保存响应原文，再按响应约定严格解析 JSON，拒绝重复键。核对每个 ID 属于本次请求的对应候选组，且在组内唯一。模型调用失败或任一校验失败时，记录原因并停止交接。
4. 保存通过校验的分组选择，按交接字段返回结果。需要换版时按任务 2.1 检查预算，固定新快照后从初选重做。

## 受控验收

使用正式快照和可捕获请求的假模型，从初选入口验收。

| 情形 | 核对结果 |
| --- | --- |
| 捕获模型请求 | 请求含初选指令和完整问题分析，两组候选与 `catalog()` 逐项一致，正式首版含 65 条算法和 35 条案例。初选仅调用目录读取入口。 |
| 两组有选择或单组为空 | 交接保留分组、组内顺序、理由及提取后的 ID。记录能回读本次目录版本、完整请求和响应原文。 |
| 两组均为空 | 交接空 ID 列表及本次目录版本，记录「本轮未选中材料」。 |
| 无效 JSON、重复键、缺组、额外字段、字段类型错误、空白理由、ID 错组、目录外 ID 或重复 ID | 记录响应原文和失败原因，拒绝整批交接。 |
| 快照失效或未取得本次目录成功事件 | 记录失败原因，模型调用次数为零。 |
| 模型调用报错 | 留存本次请求及调用错误，停止交接。 |

实现完成后，从项目根目录运行新增验收与现有读取器回归测试。

```powershell
python -B -m pytest -q -p no:cacheprovider tests/test_p1_retriever.py tests/test_p1_retrieval_snapshot.py tests/test_p1_library_reader.py
```

## 真实试跑

任务 2.2 以受控验收和读取器回归通过为完成条件。真实试跑依赖任务 3 的预算预检和结算，使用本页 CVRP 样例。

1. **核对预算。** 确认模型及版本，对拟提交的完整请求计量 token 或作有依据的保守估算。检查输入与预留输出之和是否符合模型上下文上限和账本余额。无法可靠预检或预算不足时，记录原因并停止调用。通过预检后提交同一个请求，并按 API 实际用量结算。[P1阶段计划任务 3](P1-五角色与开发调试.md)
2. **复核相关性。** 逐项对照选中条目的目录与理由，检查是否覆盖客户排列解码和解码后局部改进两项需求，记录未覆盖的需求和缺乏依据的理由。`ALG-001` 和 `CASE-001` 可作参照，也接受满足相同需求且理由有目录依据的选法。相关性不足时，依据记录调整初选指令并在获准预算内复核。具体适用条件和引用由任务 2.3 按全文核验。
3. **确定批次配额。** 结合试跑用量、初选覆盖及任务 2.3 的全文预算，确定正式批次的选取上限和输出额度。重试上限与记录持久化按任务 3 确定。
