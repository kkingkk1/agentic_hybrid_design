# CASE-001：HGS-CVRP 的交叉、解码与局部搜索

**案例文件：** [CASE-001.json](CASE-001.json) 使用四字段模板，`description` 以代码行为为准；本页保留论文依据、版本差异和使用边界。两者共同对应一个校准案例。

**摘要：** 对 CVRP 客户排列交叉并用 Split 解码，局部搜索后先入池；不可行后代可进一步修复。搜索允许超容量，目标是返回找到的最好可行解。

**记录范围与问题结构：** 本条记录 HGS-CVRP 的核心搜索及种群反馈。原问题为单仓库、有容量和车辆数上限的车辆路线问题；每个客户访问一次，各路线从仓库出发并返回，目标为总路线距离最小。搜索可对超容量路线施加罚项；具体运行时应核对所用实现的车辆数和距离设置。

**组件分工与连接：**

1. 初始化时生成 $4\mu$ 个随机解，经局部搜索后按可行性进入子种群。父代选择依据解质量和多样性，从已有个体中选出两个父代。
2. [顺序交叉](../../算法条目/ALG-006/ALG-006.json)使用父代不含仓库分隔符的客户排列，输出新的客户排列。该排列交给 [Split](../../算法条目/ALG-001/ALG-001.json)，恢复路线分隔并形成后代路线方案。
3. 对后代运行路线局部搜索，包含 [SWAP*](../../算法条目/ALG-002/ALG-002.json) 和其他邻域；普通局部搜索完成后，后代先按可行性加入相应子种群。
4. 若后代不可行，论文以 50% 的概率将罚系数提高至十倍，再运行局部搜索尝试修复。论文算法 1 随后将修复结果再次入池；下方另记作者代码中的条件差异。这些比例和倍数是来源设置，不是本项目的通用默认值。
5. 按子种群规模、克隆、质量和多样性执行生存选择；定期根据局部搜索所得解的可行比例调整罚系数。按论文 §4 的 CPU 时间模式，达到无改进次数阈值后重启搜索，直到时间上限；其他模式的停止方式须分别说明。

**信息交换：** 个体同时保存客户排列和带分隔符的路线。父代向交叉提供排列；交叉向 Split 传递新排列；Split 向局部搜索传递分段路线；普通局部搜索结果向种群管理传递路线及可行性；局部搜索结果的可行比例反馈到容量违规罚系数。

**与算法实现的关系：** 案例中的 `Split::generalSplit` 接收新排列及第一父代的路线数，并将解码使用的车辆数上限设为该路线数与总需求除以容量向上取整值中的较大者。它先尝试普通 Split，不能按该上限恢复分段时再尝试有限车辆版本；其容量超限使用罚项。[ALG-001](../../算法条目/ALG-001/ALG-001.json) 的项目参考代码实现硬容量、车辆数不限的基本情形，两者体现相关解码机制，但不是同一份代码，接口和约束不能直接互换。

**论文与代码的差异：** [作者公开的 HGS-CVRP v1.0.0 代码](https://github.com/vidalt/HGS-CVRP/blob/35b32d8e9552074f52444d51ea1fe8aec9055467/Program/Genetic.cpp#L11-L18)同样先插入普通局部搜索的后代，但仅在修复结果可行时再次入池。论文算法 1 未写出这一额外判断；引用时须区分论文伪代码和此代码版本。
