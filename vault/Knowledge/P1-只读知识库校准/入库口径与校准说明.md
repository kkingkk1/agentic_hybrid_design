初次核查日期：2026-11-07；算法和案例文件格式修订日期：2026-11-12；英文版与目录迁移日期：2026-11-13；算法字段修订日期：2026-11-14。实际复核的来源、版本、形式和日期见各条目。

本页与条目是建设前的校准材料，样例和口径待研究者审阅，不是冻结的百级知识库。来源按各条目记录的版本、章节和可读取形式核对；条目是否计入正式库，仍须在扩充时按下列口径复核。两库建成后对设计批次保持静态只读；本批算法、代码、实验和反思另存，不作为外部库条目回写。

## 样例与按 ID 查找

每条算法或案例以 ID 命名目录，目录内保存该条目的 JSON、同 ID 的 Markdown 来源记录及已有代码、验证文件。工作库位于项目顶层的 [library/working/calibration](../../../library/working/calibration/)；本页和审阅资料仍保存在 `vault`。案例说明还记录组合和迁移限制。为多个条目共用的论文资料保留在资料目录，由各条目的来源记录引用。下列链接指向当前校准草稿；读取器默认使用本页下方说明的英文冻结快照，草稿后续修改不会自动改变该快照。检索时算法摘要和案例描述均取自 JSON。阅读与按 ID 查找不依赖数据库、在线服务或新增软件。

## 收录、去重与来源

**两库职责。** 算法库提供可复用的方法和对应实现；案例库说明这些方法怎样组合成完整流程，并保留案例完整实现供核查。两库分别服务于组件复用和组合设计，不以一份案例代码替代算法条目的实现。

**跨库实现关系。** 每份工作库及其冻结快照内部，同一版本的实现只保存一份：共享组件放在算法条目，案例专有代码放在案例条目。案例通过算法 ID、文件路径和内容哈希引用共享文件；读取器核对后组装完整案例代码。冻结快照是保留版本的副本，不增加条目数。存在不同实现或变体时，分别保存并写清接口、约束和行为差异，不将关联自动等同于代码一致。

**条目粒度。** 算法条目可以是完整方法、组件或算子，但必须能够独立说明职责、输入输出、机制、适用条件、开销与限制，并提供该粒度的完整参考实现及必要依赖；组件不必独自构成求解器。案例条目对应一项有出处的组合设计，必须说明原问题、组件分工、连接和触发、传递信息与限制；只有方法名称列表或摘要不足以核实耦合的材料，仅列为线索。

**必要信息。** 样例以支持检索、理解和组合设计为目的。算法条目应交代层级、问题与前提、职责及语义上的输入输出、核心机制、限制、开销和对应代码，注明代码的来源或自主实现、版本、依赖、适用范围与验证情况。案例条目应提供完整算法代码和必要辅助实现，并说明记录范围、原问题、组件职责、连接时序、传递信息及适用条件；不要求来源实现已适配本项目接口。存在共享状态、条件分支或反馈时写明其作用。来源与关联单独可查；案例中的组件若尚未单独入库，可写名称、职责和出处，不虚构 ID。

**实现与介绍一致。** 算法条目的摘要和正文须对应同目录实际登记的代码，明确实现粒度、入口、输入、输出、约束、失败或无解返回及调用方职责。多个函数共同完成一项机制时，须写明各函数和分工；不能把整个求解流程的接口写成单个组件的接口。论文或案例有额外能力、不同接口或不同复杂度时，须明确标为对应来源的机制，不得写成当前代码已实现。条目内容或代码变化后重新核对摘要、正文、来源说明和文件版本；无法核实的内容标为待补，不宣称已同步。

关键机制、约束、输入输出或组合连接无法核实时，只保留为线索。算法缺少对应粒度的实现及必要辅助内容时暂列待补，不计为满足新口径的正式算法；只有论文描述、源码入口、片段或缺少必要实现的包装，也不能作为符合完整模板的案例。非关键性能数值、精确内存界或未确定的默认参数可以缺省，并按需要标明未知。项目新增的接口约定和迁移建议须与来源原有事实区分。

### 算法文件格式

算法采用 UTF-8 JSON，包含以下字段：

- `algorithm_id`：字符串，例如 `ALG-001`。
- `category`：英文方法类别的字符串数组；一条可有多个类别。
- `summary`：英文字符串，概括当前实现的方法名称、适用问题、主要职责及必要边界，供检索时判断；不能把源文中未实现的能力写成代码功能。
- `description`：英文文本片段数组，说明条目层级、职责与接口、机制、适用条件、限制、开销和相关条目。读取时直接拼接各片段，保留片段内空格、换行和公式。
- `code`：对象，记录实现入口 `entry`、语言 `language`、来源性质 `origin`，以及 `files` 数组。数组中逐文件记录相对于该 JSON 的 `path` 和 `sha256_lf`；哈希按源文件字节将 CRLF 转为 LF 后计算 SHA-256。实现代码保存在同一条目目录内，不把代码片段当作完整实现。

JSON 是算法描述和代码位置的主要记录；同 ID 的英文 Markdown 单独保存来源版本、核查依据、依赖和验证范围，不再重复维护算法正文。案例来源说明也使用英文。代码和原始许可证保留现有版本，代码中的原有注释可能不是英文。需要核对出处或版本时，应同时读取该来源记录。JSON、代码文件和来源记录共同对应一个算法条目。[读取器](../../../scripts/p1_library_reader.py)按登记路径和哈希加载代码，不执行代码。

参考实现尚无统一运行接口，包含 C++ 和 Python 代码。部分 Python 函数返回 `Fraction`、`set` 或 `frozenset`，不能直接作为 JSON 数值或数组序列化；调用方需要按目标接口选择保留精度和集合语义的转换方式。各条目的输入前提和输出约定以对应 JSON 与代码为准。

### 案例文件格式

案例参照本机 `roco_paperbanana/vault/Knowledge/案例入库与接口适配.md` 中的模板，采用 UTF-8 JSON，固定四个字段：

- `case_id`：字符串，例如 `CASE-001`。
- `category`：简短字符串，概括主要组合方法，不表示可行性或性能。
- `description`：英文文本片段数组。按实际实现分阶段描述问题、组件分工、调用顺序、传递数据、触发与反馈、接受及停止规则；只写实现覆盖的内容。关联算法时写明 ID 及是否属于同一实现或存在变体差异；尚未入库的组件写名称和作用，不虚构 ID。用途和取舍有证据时可以简述，不虚构作者意图或实验收益。
- `code`：按完整案例的文件顺序排列的文件记录数组。每项以 `name` 指定还原后的文件名，以 `path` 和 `sha256_lf` 指定源码文件及其 LF 归一化后的 SHA-256。案例自身文件的 `path` 相对案例目录；引用算法文件时另写 `algorithm_id`，`path` 必须是该算法条目已登记的路径，哈希也须与算法条目一致。可选的 `marker` 指定文件分隔符前缀 `#` 或 `//`，省略时为 `//`。清单应包含完整算法、必要辅助实现及许可文件；不以入口片段或外部链接代替实现。现有案例均使用文件清单；读取器仍兼容历史版本的源码行数组。

读取时直接拼接 `description` 片段。文件清单中的各项由读取器校验哈希后，按顺序以指定前缀的 `--- FILE: 路径 ---` 标记分隔并拼接；文件内容的 CRLF 统一转为 LF。历史源码行数组以换行符拼接，保留其中的空格、空行和末尾空字符串。多文件代码需按标记恢复各文件，不能作为单一源文件直接运行。案例的 JSON 与其锁定的文件共同决定案例内容；同 ID 的 Markdown 记录问题结构、来源版本、使用条件、依赖、已知缺陷、迁移边界及 JSON 文件的 SHA-256。JSON 的字节哈希包含行尾；仓库以 `.gitattributes` 固定案例 JSON 检出为 LF，修改 JSON 或转换行尾后仍应重新计算并记录对应版本。JSON 与来源记录共同对应一个案例，不重复计数。

来源、许可和代码适用范围须核查到具体版本。研究者确认，本项目两库中可读取的摘要、正文、代码、来源说明和共享文件均可发送给外部模型，不另设逐条外发许可状态或拦截。外部模型使用须满足相应许可和服务条件。案例提供参考实现，不表示已通过本项目接口、可行性验证或性能评价。

**分类。** 算法库保留一个库，通过方法类别组织，不为每个类别拆建独立库。同一条目可以有多个类别；标签不增加条目数，也不把算子或控制机制当成完整算法。

区分条目层级、方法类别和功能：层级说明完整方法或组件，算子、解码器和控制机制是组件的具体职责；类别描述所用方法；功能说明它在组合中的作用。问题及关键前提写入摘要和正文，不依赖标签隐含表达。

方法类别先按以下方向组织，后续可依据实际材料补充：

- 启发式与元启发式（`Heuristics and metaheuristics`），包括构造启发式、局部搜索、遗传算法和模拟退火等。
- 树搜索（`Tree search`），包括分支定界、束搜索等；是否完整搜索或具备最优性保证须按具体方法说明。
- 动态规划（`Dynamic programming`），例如固定访问顺序下的 Split 解码。
- 约束规划（`Constraint programming`），例如约束传播和基于约束的搜索。
- 数学规划与问题松弛（`Mathematical programming and relaxation`），例如整数规划、线性松弛和拉格朗日松弛；不因此引入商业求解器依赖。
- 图算法（`Graph algorithms`），例如最短路和网络流。分解方法可按实际机制标注相应类别，并在摘要和正文说明其作用。

条目在组合中的作用，例如构造与修复、表示与解码、局部改进、重组与扰动、搜索控制及分解协调，按实际职责写入摘要和正文，不设单独的功能标签。方法类别用于浏览与检查覆盖。案例库仍独立记录各方法的连接、信息交换及条件。分类参考[Blum 等的混合算法综述](https://doi.org/10.1016/j.asoc.2011.02.032)，但项目允许不含元启发式的方法组合。

按[P1阶段计划](../../Plan/P1-五角色与开发调试.md)任务2，程序向 Retriever 提供全部算法摘要和案例描述，再由其选择 ID；类别标签供判断时参考，不用于首版程序预筛选。分类是否改善检索效果尚未验证。

**ID。** 算法使用 `ALG-` 加三位数字，案例使用 `CASE-` 加三位数字；两类各自递增。ID 在库内唯一，文件名使用完整 ID。编号标识条目而非论文、实例或代码文件；后续修订保留原 ID，不把改参数或改语言视作新条目。校准样例保留各冻结快照供追溯；正式库的版本与保留方式在任务 3 确定。

**去重。** 先按名称、别名和来源查找候选，再比较机制、职责、输入输出、约束及组合关系。仅改名、参数、随机种子、实例或实现语言，通常合并为一条；实质不同的算子或组合可分别计数。若是否独立不能确定，保留待核查状态，不计入正式数量。一个来源同时支持组件与整体案例时可跨库引用，但各条必须提供不同用途。

**本批关联与去重复核。**

- ALG-001 解释固定排列的路线解码；ALG-002 解释跨路线交换；CASE-001 解释交叉、解码、局部搜索与种群反馈。它们有可区分的接口或组合关系，不因引用同一 HGS 文献而合并。ALG-001 还以 Split 专文核对机制。
- ALG-003 和 ALG-004 分别解释 ALNS 论文中的算子选择与 Regret-k 插入；CASE-002 记录第三方变体的组合实现。该变体的评分和精修策略与论文不同，关联按各自实际机制理解。

- ALG-006 重组父代排列；ALG-007 根据目标差决定是否接受候选；ALG-008 按请求相关性移除，ALG-009 按当前移除收益移除。它们职责不同；CASE-001 和 CASE-002 记录这些机制在各自完整实现中的连接及变体差异。

**来源与证据。** 每条记录作者、公开来源或 DOI、实际核对的版本与位置，以及核查日期；案例另记录代码仓库、固定版本、许可、依赖及任何本地改动。不使用 E1/E2/E3 等证据等级标签。转述来源时应说明实际读过的材料，不把转述写成本次直接核对原文。关键机制须能从正文、伪代码或实现追溯。论文摘要、题名或零散片段无法支持必要细节时不作为正式条目。同一来源的正式版与作者稿应标明关系和实际读过的版本，不把期刊年份写成作者稿日期。复制、修改、运行或分发材料须遵守对应版本的使用条件。

**计数。** 现有算法校准样例 33 条、案例校准样例 10 条，共 43 条；本批新增 8 条案例。33 条算法样例均已提供参考实现和相应验证记录。六类算法样例分别为启发式与元启发式 8 条，其余五类各 5 条。案例按来源说明分别记录了已知缺陷和验证范围，样例数量不等于正式建库已完成。扩充时复核通过的样例至多各计一次；未通过、重复、只有线索或占位的材料不计入正式数量。记录每批新增和去重后的两库实际数量，分别报告问题与方法覆盖及剩余缺口。

## 读取器使用

2026-11-14 已保存[当前英文校准快照](../../../library/versions/calibration-20261114-03-en/)和对应[冻结清单](../../../library/manifests/calibration-20261114-03-en/manifest-6e20a83e63570d7f9ae40ddfece9cc86c63e73b5db8078b7a987a562d00f2d26.json)。该版本包含 33 条算法、10 条案例和条目目录内的 275 个文件；清单按文件原始字节记录大小和 SHA-256，并固定条目 ID 集合。快照与清单须一同保留；快照内部继续通过算法条目保存共享文件，不把引用复制到案例目录。

[上一英文快照](../../../library/versions/calibration-20261113-02-en/)和[对应清单](../../../library/manifests/calibration-20261113-02-en/manifest-a3654379174a37407eec67b1cdc117683d590d026737456f5744c4ca427a5f91.json)保留原有功能标签；当前快照以它为父版本，仅从算法 JSON 移除该字段。[原校准快照](../../../library/versions/calibration-20261113-01/)和[原清单](../../../library/manifests/calibration-20261113-01/manifest-12a68128f249ef58fc264e7173652ca3f95b7cff3788578dd7d1442c43c43d5c.json)保留翻译前内容。

该快照用于恢复本批条目及来源说明，不表示样例已通过正式库验收。项目级论文 PDF 和解析资料不在快照中；来源记录仍链接项目现有资料，其内容变化不受本清单校验。

在项目根目录运行：

```powershell
python -B scripts/p1_library_reader.py catalog
python -B scripts/p1_library_reader.py load ALG-001 CASE-001
```

Python 代码也可调用同一接口：

```python
from scripts.p1_library_reader import DRAFT_ROOT, LibraryReader

reader = LibraryReader()
candidates = reader.catalog()
materials = reader.load(["ALG-001", "CASE-001"])
```

读取器默认使用上述当前校准快照和冻结清单。命令行的 `catalog` 以 UTF-8 JSON 输出全部算法的 ID、类别和摘要，以及全部案例的 ID、类别和完整描述；Python 接口返回对应字典。读取历史快照时，若原条目含 `function`，候选目录保留该字段。案例没有单独摘要字段。候选列表不包含代码，也不按类别、关键词或向量预筛选。

整理未冻结的校准工作库时，可运行 `python -B scripts/p1_library_reader.py --draft catalog`，或在 Python 中使用 `LibraryReader(DRAFT_ROOT, manifest=None)`；草稿模式不执行冻结清单校验。`--root` 可指定另一份目录，默认仍使用当前冻结清单；另选清单时在子命令前提供 `--manifest`。读取历史快照时须同时指定其目录与对应清单。恢复快照时可将条目目录复制到新的空目录，并使用对应清单与 `--root` 核验；复制到不同层级时，来源说明中指向项目级资料的相对链接也需保持可访问。

`load` 按所给 ID 顺序返回完整条目；命令行输出 JSON，Python 接口返回列表。每项的 `entry` 包含拼接后的描述和完整代码，`json_file` 与 `source` 记录相对路径和文件原始字节的 SHA-256；`source.content` 是完整来源说明。算法代码保存在 `entry.code.files` 各项的 `content` 中，案例代码保存在 `entry.code`。算法代码哈希按 CRLF 转 LF 后核对，返回的代码保留原始换行；文件清单形式的案例代码按前述方式归一化并组装。案例读取器从来源说明中查找唯一的 `SHA-256 is` 或旧版 `SHA-256 为`，其后接反引号包裹的 64 位十六进制哈希，并与 JSON 原始字节核对；引用算法时还校验登记路径和锁定哈希。条目缺失、ID 重复或无效、路径越出所属目录、格式错误或版本不符时，整个加载请求报错，不省略条目或代码。

冻结模式下，读取器每次验证清单文件名中的 SHA-256 和实际条目集合。`catalog` 对全部候选 JSON 核对原始字节；`load` 对所选条目的 JSON、来源说明、实际读取的源码及共享引用逐一核对。未用于本次读取的文件不会逐一加载；初次冻结时已逐文件核对完整快照。清单或实际读取内容不符时直接报错，不返回部分结果。文件仍可被操作系统修改；哈希用于发现变化，不是访问控制，也不自动恢复内容。

读取器只提供材料，不判断相关性或计算模型 token。正式检索仍须在初选前固定并记录本次快照及实际材料版本；单独记录 Git commit 不能证明工作目录的实际内容。调用前计量或可靠估算完整输入、预留输出并检查预算，调用后按 API 实际用量结算。无法可靠检查或超限时停止相应调用，不截断；预算规则见[P1阶段计划](../../Plan/P1-五角色与开发调试.md)任务3。Retriever 先看全部候选，再依据实际收到的材料分析适用条件、组合建议和证据缺口。案例提到某算法不等于该算法条目已加载；补读与引用边界按同一计划任务2执行。正式检索的快照管理、模型交接、补读调度、预算计量和引用校验尚未接入。

## 待扩充范围与首版数量建议

**已确定：** 两库合计按百级规划；优先 TSP、CVRP 和有明确迁移依据的组合优化方法。本批按研究者要求覆盖六类，每类至少提供 5 条算法样例；原有 8 条启发式与元启发式样例保留，后续扩展不要求固定比例。单条内容须符合上述入库口径；原文问题不同于目标问题时，应明确需改写和重新验算的条件。

**建议，待研究者决定：** 首版目标合计 **100 条**，其中算法 **65 条**、案例 **35 条**。该比例为便于开始分批整理的工作建议，不是已核定预算、数量或质量门槛；案例需要核对组件之间的信息交换，通常比只摘名称更费核查工作。现有 43 条尚未测得稳定的整理工时或来源命中率，不能据此推算完成日期或成本。若研究者选择其他目标，按实际决定替换建议。

**建议的优先覆盖：** 先补 TSP 和 CVRP 的构造、表示与解码、局部改进、重组与扰动，以及相应的组合案例；再补容量等约束处理、控制与接受、分解协调和适用的精确子问题。外部问题的材料只有说清表示、约束和信息接口如何迁移，才能作为可迁移参考，不能仅因都属于组合优化就认定适用。

**当前可保留的缺口：** 样例包含一个调用 CP-SAT 的路径精修变体，但其效果与正确性尚未在本项目验证；精确子问题已做小规模核验，但尚未接入项目接口或用目标问题实例评价；仍无经过验证的分解协调案例。算法库中 TSP 直接适用的局部改进目前只有 2-Opt，案例中的其他局部搜索尚未作为独立算法条目整理；精确 TSP 方法适用于小规模完全图，排列交叉须按具体表示使用。新增 TSP、CVRP、VRPTW 及可配置车辆路径案例仍需逐条审阅，部分代码已发现缺陷或尚未完整运行。CASE-002 的 ALNS 变体来自 PDPTW，并非 CVRP 实现。大量潜在方向、来源及其许可仍未核查；数量不足或材料不可核实时，按实际缺口报告，不以占位条目补数。
