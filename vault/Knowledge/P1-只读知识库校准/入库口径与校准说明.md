## 样例与按 ID 查找

每条算法或案例以 ID 命名目录，目录内保存该条目的 JSON、同 ID 的 Markdown 来源记录及已有代码、验证文件。案例说明还记录组合和迁移限制。为多个条目共用的论文资料保留在资料目录，由各条目的来源记录引用。下列清单用于按 ID 导航；检索时算法摘要和案例描述均取自 JSON。阅读与按 ID 查找不依赖数据库、在线服务或新增软件。

## 收录、去重与来源

**两库职责。** 算法库提供可复用的方法和对应实现；案例库说明这些方法怎样组合成完整流程，并保留案例完整实现供核查。两库分别服务于组件复用和组合设计，不以一份案例代码替代算法条目的实现。

**条目粒度。** 算法条目可以是完整方法、组件或算子，但必须能够独立说明职责、输入输出、机制、适用条件、开销与限制，并提供该粒度的完整参考实现及必要依赖；组件不必独自构成求解器。案例条目对应一项有出处的组合设计，必须说明原问题、组件分工、连接和触发、传递信息与限制；只有方法名称列表或摘要不足以核实耦合的材料，仅列为线索。

**必要信息。** 样例以支持检索、理解和组合设计为目的。算法条目应交代层级、问题与前提、职责及语义上的输入输出、核心机制、限制、开销和对应代码，注明代码的来源或自主实现、版本、依赖、适用范围与验证情况。案例条目应提供完整算法代码和必要辅助实现，并说明记录范围、原问题、组件职责、连接时序、传递信息及适用条件；不要求来源实现已适配本项目接口。存在共享状态、条件分支或反馈时写明其作用。来源与关联单独可查；案例中的组件若尚未单独入库，可写名称、职责和出处，不虚构 ID。

关键机制、约束、输入输出或组合连接无法核实时，只保留为线索。算法缺少对应粒度的实现及必要辅助内容时暂列待补，不计为满足新口径的正式算法；只有论文描述、源码入口、片段或缺少必要实现的包装，也不能作为符合完整模板的案例。非关键性能数值、精确内存界或未确定的默认参数可以缺省，并按需要标明未知。项目新增的接口约定和迁移建议须与来源原有事实区分。

### 算法文件格式

算法采用 UTF-8 JSON，包含以下字段：

- `algorithm_id`：字符串，例如 `ALG-001`。
- `category`、`function`：分别保存方法类别和功能标签的字符串数组；一条可有多个标签。
- `summary`：字符串，概括方法名称、适用问题、主要职责及必要边界，供检索时判断。
- `description`：中文文本片段数组，说明条目层级、职责与接口、机制、适用条件、限制、开销和相关条目。读取时直接拼接各片段，保留片段内空格、换行和公式。
- `code`：对象，记录实现入口 `entry`、语言 `language`、来源性质 `origin`，以及 `files` 数组。数组中逐文件记录相对于该 JSON 的 `path` 和 `sha256_lf`；哈希按源文件字节将 CRLF 转为 LF 后计算 SHA-256。实现代码保存在同一条目目录内，不把代码片段当作完整实现。

JSON 是算法描述和代码位置的主要记录；同 ID 的 Markdown 单独保存来源版本、核查依据、依赖和验证范围，不再重复维护算法正文。需要核对出处或版本时，应同时读取该来源记录。JSON、代码文件和来源记录共同对应一个算法条目。[读取器](../../../scripts/p1_library_reader.py)按登记路径和哈希加载代码，不执行代码。

参考实现尚无统一运行接口。部分函数返回 Python 的 `Fraction`、`set` 或 `frozenset`，不能直接作为 JSON 数值或数组序列化；调用方需要按目标接口选择保留精度和集合语义的转换方式。各条目的输入前提和输出约定以对应 JSON 与代码为准。

### 案例文件格式

案例参照本机 `roco_paperbanana/vault/Knowledge/案例入库与接口适配.md` 中的模板，采用 UTF-8 JSON，固定四个字段：

- `case_id`：字符串，例如 `CASE-001`。
- `category`：简短字符串，概括主要组合方法，不表示可行性或性能。
- `description`：英文文本片段数组。按实际实现分阶段描述问题、组件分工、调用顺序、传递数据、触发与反馈、接受及停止规则；只写实现覆盖的内容。关联算法时写明 ID 及是否属于同一实现或存在变体差异；尚未入库的组件写名称和作用，不虚构 ID。用途和取舍有证据时可以简述，不虚构作者意图或实验收益。
- `code`：完整算法及必要辅助实现的源代码行数组。多文件实现按明确的文件边界放入同一数组，并保留版权与许可声明；不以入口代码、片段或外部链接代替实现。

读取时直接拼接 `description` 片段，以换行符拼接 `code` 行；保留片段空格、空行和末尾空字符串。多文件代码需按标记恢复各文件，不能作为单一源文件直接运行。案例的 JSON 以自身内容为准；同 ID 的 Markdown 记录问题结构、来源版本、使用条件、依赖、已知缺陷、迁移边界及 JSON 文件的 SHA-256。字节哈希包含行尾；修改 JSON 或转换行尾后应重新计算并记录对应版本。两份文件共同对应一个案例，不重复计数。

来源、许可和代码适用范围须核查到具体版本。外部模型使用须满足相应许可和服务条件；条件不明时不作为已获准外发处理。案例提供参考实现，不表示已通过本项目接口、可行性验证或性能评价。

**分类。** 算法库保留一个库，通过类别和功能标签组织，不为每个类别拆建独立库。同一条目可以有多个类别或功能标签；标签不增加条目数，也不把算子或控制机制当成完整算法。

区分条目层级、方法类别和功能：层级说明完整方法或组件，算子、解码器和控制机制是组件的具体职责；类别描述所用方法；功能说明它在组合中的作用。问题及关键前提写入摘要和正文，不依赖标签隐含表达。

方法类别先按以下方向组织，后续可依据实际材料补充：

- 启发式与元启发式，包括构造启发式、局部搜索、遗传算法和模拟退火等。
- 树搜索，包括分支定界、束搜索等；是否完整搜索或具备最优性保证须按具体方法说明。
- 动态规划，例如固定访问顺序下的 Split 解码。
- 约束规划，例如约束传播和基于约束的搜索。
- 数学规划与问题松弛，例如整数规划、线性松弛和拉格朗日松弛；不因此引入商业求解器依赖。
- 图算法，例如最短路和网络流。分解方法可按实际机制标注相应类别，并用分解协调功能说明其作用。

功能标签描述条目在组合中的作用，例如构造与修复、表示与解码、局部改进、重组与扰动、搜索控制及分解协调；具体标签按条目职责填写。类别和功能用于理解条目、浏览与检查覆盖。案例库仍独立记录各方法的连接、信息交换及条件。分类参考[Blum 等的混合算法综述](https://doi.org/10.1016/j.asoc.2011.02.032)，但项目允许不含元启发式的方法组合。

**ID。** 算法使用 `ALG-` 加三位数字，案例使用 `CASE-` 加三位数字；两类各自递增。ID 在库内唯一，文件名使用完整 ID。编号标识条目而非论文、实例或代码文件；后续修订保留原 ID，不把改参数或改语言视作新条目。冻结后的版本与保留方式在任务 3 确定。

**去重。** 先按名称、别名和来源查找候选，再比较机制、职责、输入输出、约束及组合关系。仅改名、参数、随机种子、实例或实现语言，通常合并为一条；实质不同的算子或组合可分别计数。若是否独立不能确定，保留待核查状态，不计入正式数量。一个来源同时支持组件与整体案例时可跨库引用，但各条必须提供不同用途。

**来源与证据。** 每条记录作者、公开来源或 DOI、实际核对的版本与位置，以及核查日期；案例另记录代码仓库、固定版本、许可、依赖及任何本地改动。关键机制须能从正文、伪代码或实现追溯。论文摘要、题名或零散片段无法支持必要细节时不作为正式条目。同一来源的正式版与作者稿应标明关系和实际读过的版本，不把期刊年份写成作者稿日期。复制、修改、运行或分发材料须遵守对应版本的使用条件。

## 读取器使用

在项目根目录运行：

```powershell
python -B scripts/p1_library_reader.py catalog
python -B scripts/p1_library_reader.py load ALG-001 CASE-001
```

Python 代码也可调用同一接口：

```python
from scripts.p1_library_reader import LibraryReader

reader = LibraryReader()
candidates = reader.catalog()
materials = reader.load(["ALG-001", "CASE-001"])
```

命令行的 `catalog` 以 UTF-8 JSON 输出全部算法的 ID、类别、功能和摘要，以及全部案例的 ID、类别和完整描述；Python 接口返回对应字典。案例没有单独摘要字段。候选列表不包含代码，也不按类别、关键词或向量预筛选。可通过命令前的 `--root` 参数指定另一份知识库目录；Python 调用可向 `LibraryReader` 传入该目录。

`load` 按所给 ID 顺序返回完整条目；命令行输出 JSON，Python 接口返回列表。每项的 `entry` 包含拼接后的描述和完整代码，`json_file` 与 `source` 记录相对路径和文件原始字节的 SHA-256；`source.content` 是完整来源说明。算法代码保存在 `entry.code.files` 各项的 `content` 中，案例代码保存在 `entry.code`。算法代码哈希按 CRLF 转 LF 后核对，返回的代码保留原始换行。案例读取器从来源说明中查找唯一的 `SHA-256 为` 后接反引号包裹的 64 位十六进制哈希，并与 JSON 原始字节核对。条目缺失、ID 重复或无效、路径越出条目、格式错误或版本不符时，整个加载请求报错，不省略条目或代码。

读取器只提供材料，不判断相关性，也不冻结库或计算模型 token。调用方须先固定本次知识库版本；在实际模型输入组装后按所用模型核算输入及总预算，超出时停止，不截断。Retriever 先看全部候选，再依据所选条目的全文分析适用条件、组合建议和证据缺口；模型交接及记录尚未接入。

## 待扩充范围与首版数量建议

**已确定：** 两库合计按百级规划；优先 TSP、CVRP 和有明确迁移依据的组合优化方法。本批按研究者要求覆盖六类，每类至少提供 5 条算法样例；原有 8 条启发式与元启发式样例保留，后续扩展不要求固定比例。单条内容须符合上述入库口径；原文问题不同于目标问题时，应明确需改写和重新验算的条件。

**建议，待研究者决定：** 首版目标合计 **100 条**，其中算法 **65 条**、案例 **35 条**。该比例为便于开始分批整理的工作建议，不是已核定预算、数量或质量门槛；案例需要核对组件之间的信息交换，通常比只摘名称更费核查工作。现有 35 条尚未测得稳定的整理工时或来源命中率，不能据此推算完成日期或成本。若研究者选择其他目标，按实际决定替换建议。

**建议的优先覆盖：** 先补 TSP 和 CVRP 的构造、表示与解码、局部改进、重组与扰动，以及相应的组合案例；再补容量等约束处理、控制与接受、分解协调和适用的精确子问题。外部问题的材料只有说清表示、约束和信息接口如何迁移，才能作为可迁移参考，不能仅因都属于组合优化就认定适用。

**当前可保留的缺口：** 样例包含一个调用 CP-SAT 的路径精修变体，但其效果与正确性尚未在本项目验证；新增精确子问题已做小规模核验，但尚未接入项目接口或用目标问题实例评价；仍无经过验证的分解协调案例。TSP 直接适用的局部改进目前只有 2-Opt；新增的精确 TSP 方法适用于小规模完全图，排列交叉须按具体表示使用。CVRP 仅有一个案例。ALNS 变体来自 PDPTW，并非 CVRP 实现；大量潜在方向、来源及其许可仍未核查。数量不足或材料不可核实时，按实际缺口报告，不以占位条目补数。
