# CASE-002: Third-party ALNS and CP-SAT variant for PDPTW

**Case file:** [CASE-002.json](CASE-002.json) uses the four-field template. This page records code provenance, differences from the paper, and observed limitations. Together they constitute one calibration case.

**Summary:** A third-party implementation applies adaptive removal, insertion, and simulated annealing to pickup and delivery with time windows and periodically attempts to reorder one route using CP-SAT. It is not the authors' implementation of the 2006 ALNS paper.

**Problem and combination:** Each order has pickup and delivery nodes. The code checks route capacity, time windows, duration, orders per vehicle, and pickup-delivery order; its objective computes route distance and fixed vehicle cost. Initial construction sorts by delivery-window deadline and greedily inserts orders. Search selects removal and repair operators independently by weight. Four removals are random, relatedness, contribution, and whole-route; repairs are greedy, Regret-2, and noisy insertion. Candidates are discarded if repair fails or the implementation's feasibility check fails; others face simulated-annealing acceptance, and operators receive scores based on best solution, current-solution improvement, or acceptance. Each segment updates weights and cools the temperature.

**Refinement and stopping:** At the configured interval, when the iteration's repair passes its checks, the code attempts CP-SAT reordering route by route. A candidate route is returned after its route check. Whenever routes change and the computed cost is finite, refinement replaces the current routes; the code does not additionally require a strict total-cost improvement. Search is limited by iteration count and wall-clock checks at the start of the loop; one route refinement may overrun the overall time limit.

**Known implementation limits:** Initial construction ignores failure to insert an individual order. `all_orders_served` counts only the set of pickup nodes and cannot ensure paired pickup-delivery nodes each appear once. `total_cost` ignores failed-route-check flags and therefore does not guarantee infinite cost for infeasible routes. On 2026-11-12, small in-memory examples reproduced both a missing delivery being judged feasible and an infeasible route receiving a finite cost. A finite-cost check after refinement cannot replace independent feasibility validation. This sample is only a combination-design reference; it does not establish feasible output or trustworthy experiments. Transfer requires reimplementation or checking of those checks and target-specific handling of pickup-delivery pairing, unassigned orders, and constraints.

**Relation to paper and algorithm entries:** [ALG-003](../../algorithms/ALG-003/ALG-003.json) and [ALG-004](../../algorithms/ALG-004/ALG-004.json) explain operator selection and Regret-k in the 2006 paper. This case is a third-party implementation of similar ideas and does not claim a step-by-step paper reproduction. Those two project reference implementations were independently written and are not called by the case. Case scoring does not use the paper's solution-history novelty criterion; initialization and failed-request handling, segment cooling, objective, and CP-SAT refinement also differ. The paper's general model includes a request bank; the same mechanism cannot be assumed here.

The case's related removal uses one seed and directly chooses the most related requests, while worst removal computes and sorts once at the start. [ALG-008](../../algorithms/ALG-008/ALG-008.json) and [ALG-009](../../algorithms/ALG-009/ALG-009.json), by contrast, select iteratively using the paper's random bias, with ALG-009 also recomputing gains each time. [ALG-007](../../algorithms/ALG-007/ALG-007.json) explains simulated-annealing acceptance; its reference code lacks the case's minimum temperature. These project reference implementations are also not called by the case.

The paper's general model includes travel distance, vehicle working time, and the number of unscheduled requests in a weighted objective, and search may pass through states with unscheduled requests; the reported experiments require every request to be scheduled in the final solution. The paper chooses removal and insertion operators separately and updates weights by segment results. Refer to the two algorithm entries and the paper for those mechanisms rather than substituting them for this case's actual code.
