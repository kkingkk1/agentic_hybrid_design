# CASE-006: CVRP destroy-repair, tabu, and restart

**Case file:** [CASE-006.json](CASE-006.json) uses the four-field template; its code is assembled from a file manifest.

**Problem and flow:** The entry reads a vehicle-routing instance and selects `MultiLNSSolver`. Initial construction tries Clarke-Wright up to 5 times, then scan up to 50 times if all fail, and greedy construction if those also fail; the first successful attempt returns immediately. One iteration randomly removes 5 non-tabu customers, then reinserts them in descending demand order, usually at the feasible position with lowest incremental cost, with probability 0.02 of selecting a random feasible position. Failed repair restores the old solution. The driver updates its best record only when the candidate cost is more than 0.1 below the recorded best. It likewise considers a candidate improved only when its cost is more than 0.1 below `last_cost`; otherwise it retains the candidate with fixed probability 0.1. After stagnation it jumps from a saved solution. The entry sets search time to 15 seconds.

**Limits and transfer:** The saved best solution may not be the lowest-cost solution encountered, since improvements of at most 0.1 do not update it. A source comment calls fixed-probability retention simulated annealing, but the implementation has neither temperature nor cooling. Even rejected candidates are written to `last_cost`, affecting the next improvement decision. Default `frac_dropped` is zero, so the jump removes no customers but shuffles route order; it must not be described as large-scale default removal. The implementation also requires valid instances and states supporting the removal count; check capacity, customer coverage, and random state when transferring.
